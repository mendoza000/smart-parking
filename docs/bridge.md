# Serial bridge

The bridge translates newline-delimited Arduino JSON into WebSocket snapshots and dispatches confirmed gate commands. Run it with `node --import tsx bridge/server.ts`. It loads `.env` through Node's `loadEnvFile()` and does not require Astro to be running. Restart only the bridge after configuration or bridge-code changes; a browser connection or gate command never resets/reopens USB, and firmware must be uploaded manually.

Configuration:

- `ARDUINO_PORT` (required): serial device path, for example `/dev/ttyUSB0`.
- `ARDUINO_BAUD_RATE` (default `9600`): integer baud rate from 1 through 4,000,000.
- `WS_PORT` (default `8080`): integer TCP port from 0 through 65535 (0 selects an ephemeral port).
- `WS_HOST` (default `127.0.0.1`): bind host. Keep the default for localhost-only access; explicitly set this to expose the bridge on another interface.
- `WS_ALLOWED_ORIGINS` (default `http://localhost:4321,http://127.0.0.1:4321`): comma-separated exact browser origins permitted to send gate commands. Snapshots remain readable to originless/other-origin clients.
- `GATE_ACK_TIMEOUT_MS` (default `4000`): positive integer deadline for one movement ACK. Timeout rejects the request and asks Arduino to synchronize; the movement is never replayed.

Arduino sends one JSON object per line, e.g. `{"spots":[false,true,false,true]}`. Each spot must be a boolean and the array must contain exactly four entries. Optional barriers have `entry` and `exit` values of `open`, `closed`, or `unknown`. Invalid lines and oversized frames are ignored. The bridge sends `SYNC\n` on each serial open and again after the board boot grace period, supporting boards that reset when the serial port opens.

WebSocket clients receive a `snapshot` immediately and after updates: `spots` is `null` until valid Arduino data arrives, `connected` reports current serial availability, and `updatedAt` identifies the last valid payload. The last spot state remains available while disconnected. Before gate capability is observed the initial snapshot retains its legacy five fields. Gate-capable snapshots add `gate`, `gateReady`, and `gatePending`; readiness requires a fresh error-free `SYNC` ACK with gate state in the current serial generation.

Commands use JSON, for example `{"type":"gate-command","requestId":"dashboard-1","action":"open"}` or `{"type":"gate-command","requestId":"dashboard-2","action":"close"}`. Only exact allowlisted `Origin` values may dispatch commands; originless clients remain read-only. This Origin check mitigates cross-site WebSocket hijacking; it is **not authentication**. Keep the bridge bound to loopback unless access is limited to a trusted LAN. The bridge validates open capacity, allows one global pending move (no queue), and sends only encoded serial constants with a random wire nonce, e.g. `GATE_OPEN 8a63a02d-f912-42a2-a9f5-675a556a590c\\n`. Confirmed gate state changes only from valid Arduino messages. The owning browser receives `gate-result` with `status: confirmed` after a matching nonce/ACK/target, or `status: rejected` with errors such as `PARKING_FULL`, `GATE_BUSY`, `NOT_SYNCHRONIZED`, `ARDUINO_DISCONNECTED`, `FIRMWARE_REJECTED`, `SERIAL_WRITE_FAILED`, or `ACK_TIMEOUT`. A matching firmware error rejects that owner's request. Late/wrong ACKs cannot confirm a later request. Closing remains available when all four spaces are full. Commands accepted before a browser disconnect continue physically; the bridge remains globally busy until ACK/deadline and broadcasts later confirmed state to connected clients.

Spot transition events are derived by clients only after an initial snapshot, never by the bridge from its initial unknown state. `Origin` is not an identity check: do not expose the unauthenticated bridge to untrusted networks.

On Unix with Node.js 26.4 or newer, the bridge uses a narrowly scoped serial-port compatibility adapter: native poller events schedule a deduplicated `setImmediate` so serialport's promise-based read loop resumes promptly. This addresses the Node 26 native-callback continuation stall documented in [bindings-cpp PR #239](https://github.com/serialport/bindings-cpp/pull/239). It does not poll, add serial writes, or change the wire/snapshot contract. Restart only the bridge after upgrading the application code; the browser and Arduino firmware do not need changes. The owned virtual-serial regression tests require Python 3 on Linux and never open a physical Arduino port.

The bridge tolerates a missing/disconnected Arduino without involving Astro's server lifecycle. After a serial error it quarantines the current descriptor, ignores its data/open events, rejects any pending command, and does not construct a replacement until close succeeds (a single bounded retry timer retries failed closes). Close callback and thrown errors include the configured device path. Shutdown cancels reconnect/boot/close-retry/command timers, closes serial and WebSocket resources, and reports a serial close failure rather than treating cleanup as successful; the executable exits nonzero on that failure. Do not open the Arduino port in Arduino IDE while the bridge owns it; only one process can use the serial device at a time. See [entry gate testing](entry-gate-testing.md) for the manual firmware upload and isolated test procedure.
